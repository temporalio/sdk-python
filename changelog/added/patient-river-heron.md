Workflow code creates a Stream, appends Records to it, reads it, describes it and closes it, with `workflow.create_stream` and `workflow.get_stream`. A create and a describe run in the Store's Local Activity, with the options of `StreamConfig.workflow_call_options`. Core makes a read, an append and a close itself, with no Activity, on the Redis Store, on `MemoryStreamStore` and on a Store written in Python. Core calls a Store written in Python as a task on the Worker's event loop, never on a Workflow thread. For Workflow code, such a Store waits up to a read's `wait`, ends that wait on a cancel, gives offsets of 1 to 1024 bytes that compare in order, fences a lower epoch of a Producer, writes a resent batch once, and raises `StreamError` with a reason. Core tries a call again for up to 30 s only on `STREAM_ERROR_REASON_STORAGE_UNAVAILABLE`. Any other exception reaches Workflow code on the first try, as a non-retryable `STREAM_ERROR_REASON_STORAGE_CORRUPT` with its type in the message. `Replayer` takes the `stream_config` of the Worker's client.
The Workflow `Stream` has `read`, `read_pages` and `read_page`, so Workflow code reads a Stream with the same calls as a client. Core reads the Store inside the Workflow Task. A page that Workflow code gets in one activation has at most 256 Records, and the rest come in the next activation with no wait. A loop that asks for its next page in the same activation keeps one read open, and a read that no code waits on closes before the activation completes, so it never holds a Workflow Task open. With a `wait`, a quiet Stream gives empty pages, so a loop on a Stream that can be quiet for long uses `read_pages` and leaves after an empty page. A call that waits on a quiet Stream holds its Workflow Task open, with one Workflow Task about every 8 s. The calls of one Workflow Task write one marker in History. `StreamConfig.workflow_read_replay_from` decides whether the marker holds the Records (`StreamReplaySource.HISTORY`) or only their offsets and a digest, which a replay reads from the Store again (`StreamReplaySource.STORE`, the default). With `HISTORY`, one Workflow Task's marker holds at most 1 MiB of Records, and the read goes on in the next task.
A Workflow's append runs in Core inside the Workflow Task, with no Activity. It writes as the Workflow, with its Workflow Task as the epoch. A `producer=` of another kind raises `StreamError` with the reason `STREAM_ERROR_REASON_INVALID`.
A Workflow's close runs in Core, with no Activity, and spans two Workflow Tasks. The task that calls `close` records the intent, Core closes the Stream after the server took that task, and the next task gives the result, so a failed task closes nothing. Await the close. A graceful shutdown of the Worker waits at most 10 s for a close that the code doesn't await, and a Worker that dies when the Workflow ends loses it. An append and a close of Workflow code always carry the Workflow Task as their epoch. An append is at-least-once. After a Worker crash or an eviction, the rerun of its task can write a second copy with the epoch of the new task.
Core records metrics for the Direct calls of a Stream, such as `temporal_stream_read_total`, `temporal_stream_read_records` and `temporal_stream_close_latency`, each with the attribute `stream_store`, and `temporal_stream_close_abandoned` for a close that a graceful shutdown gave up.
Add `StreamConfig.workflow_read_ahead_bytes`, the most bytes of one read's Records that wait in the Worker for Workflow code, 4 MiB by default.
Add `StreamConfig.workflow_read_page_records`, the most Records of one read that Workflow code gets in one activation. It is 256 by default and must be 1 to 1000.
Add `StreamConfig.workflow_read_min_gap`, the least time between two batches of one read. It has no gap by default and must be at most 1 s. A gap trades latency for fewer activations of Workflow code.
Add `temporalio.exceptions.StreamReplayError`. With it in `workflow_failure_exception_types`, a replay that can't read the Records of a read from the Store again fails the Workflow, and not only the Workflow Task.
Core tries a read, an append or a close of Workflow code again while its Store is unavailable, from 100 ms up to 2 s apart, for at most 30 s. Only then does Workflow code get the retryable `StreamError`. A replay tries its Store for 5 s. If the Store stays down, only the Workflow Task fails, with `StreamReplayUnavailable`, also with `StreamReplayError` in `workflow_failure_exception_types`.
In Workflow code, `temporalio.contrib.streams.current_producer` gives the Workflow's Producer, and `BufferedAppender` writes the appends of one activation as one append, with no timer.
